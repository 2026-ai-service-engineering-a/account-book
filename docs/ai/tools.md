# 도구

## 1. 목적

에이전트에게 주는 도구 목록이 곧 능력 범위다([../../README.md](../../README.md) 4장).
그래서 도구를 늘리는 일은 기능을 늘리는 일보다 무겁게 다룬다.

정본은 흩어져 있다 — 이름과 권한은 README 4장 표, 대응 엔드포인트는
[../api-contract.md 6장](../api-contract.md#6-엔드포인트-초안). **이 문서는 그 표들이 담지
못하는 것을 정한다.** 도구 하나를 어떤 모양으로 만드는지, 결과와 오류를 모델에게 어떻게
보여주는지, 그리고 어느 자리에서 어느 도구까지 주는지.

세 기능이 전부 같은 도구를 쓴다([README.md 1장](README.md#1-세-기능)). 기능마다 도구를
따로 만들면 같은 집계가 세 번 생긴다.

## 2. 도구 하나의 모양

도구는 함수가 아니라 **스키마 둘과 설명 하나**다.

```python
# src/agent/domain/tools/count_frequency.py
class CountFrequencyInput(BaseModel):
    period: PeriodName                      # 이름만. 날짜 계산은 코드가 한다
    category_id: CategoryId | None = None
    merchant: str | None = None

class CountFrequencyOutput(BaseModel):
    count: int
    day_count: int
    avg_gap_days: float
    avg_amount: Money
```

| 부분 | 규칙 |
|---|---|
| 이름 | `동사_목적어`. `get_data` 같은 이름은 모델도 어느 자리에 쓸지 모른다 |
| 설명 | **모델이 읽는 문서다.** 한 줄로 무엇을, 한 줄로 **언제 쓰지 말아야 하는지** |
| 입력 | Pydantic. 원시 타입을 그대로 받지 않는다([../development-rules.md 5.3](../development-rules.md#53-원시-타입을-그대로-쓰지-않는다)) |
| 출력 | Pydantic. `dict`를 반환하는 도구를 만들지 않는다 |
| 권한 | 읽기 · 쓰기(확인 필요) · 쓰기(항상 확인) 셋 중 하나 |

설명의 둘째 줄이 첫째 줄보다 중요하다.

```
count_frequency — 기간 안의 거래 건수와 거래가 있던 날 수를 센다.
                  금액 합계가 필요하면 이 도구가 아니라 summarize_spending을 쓴다.
```

"쓰지 말아야 할 때"를 안 적으면 모델은 아는 도구로 모든 걸 해결하려 한다. 도구가 여덟
개일 때는 티가 안 나고, 열둘이 되면 엉뚱한 도구를 부르는 비율이 눈에 보이게 올라간다.

## 3. 모든 도구에 걸리는 규약

| 규약 | 왜 |
|---|---|
| **도구는 집계하지 않는다** | 합계·평균·증감은 `api`가 계산한 값을 옮긴다. 도구가 나누기 시작하면 같은 계산이 두 군데 생긴다 |
| **도구 하나 = 엔드포인트 하나** | 도구가 엔드포인트 둘을 엮으면 실패가 절반만 일어난다([../api-contract.md 6장](../api-contract.md#6-엔드포인트-초안)) |
| **도구는 LLM을 부르지 않는다** | 도구 안에 모델이 있으면 비용과 지연이 감사 로그에서 사라진다 |
| **도구는 재시도하지 않는다** | 재시도는 루프의 일이다(`agent-loop.md` 7장) |
| **도구는 기간 경계를 계산하지 않는다** | 이름을 받아 코드가 푼다([chat-analytics.md 5장](chat-analytics.md#5-기간--llm에게-날짜를-계산시키지-않는다)) |
| **결과에는 상한이 있다** | 3.2 |

### 3.1 결과 봉투

모든 도구는 같은 봉투로 답한다.

```json
{
  "call_id": "call_3",
  "ok": true,
  "data": { "count": 7, "day_count": 5, "avg_gap_days": 1.4 },
  "meta": { "row_count": 7, "truncated": false, "elapsed_ms": 38 }
}
```

`call_id`가 왜 필요한가 — 세 군데서 쓴다. 감사 로그(`tool_calls`)의 키가 되고, 차트 스펙이
데이터를 참조하는 이름이 되고([agentic-reports.md 5장](agentic-reports.md#5-차트-스펙--그림은-선언으로-온다)),
같은 도구를 두 번 부른 대화에서 어느 결과를 말하는지 가린다.

### 3.2 크기 상한

컨텍스트는 예산이다. 도구가 3년치를 돌려주면 그 한 번으로 예산이 끝난다.

- 목록형 도구는 기본 20행, 최대 50행. 계약의 페이지네이션 상한보다 **더 좁게** 잡는다 —
  화면은 200행을 그릴 수 있지만 모델이 200행을 읽을 이유는 거의 없다.
- 직렬화 결과가 8KB를 넘으면 자르고 `meta.truncated = true`를 세운다.
- 잘렸으면 모델에게 그 사실을 문장으로도 알린다 — "50건까지만 보여줬다. 기간을 좁혀라."
  조용히 자르면 모델은 그게 전부라고 믿고 답한다.

금액은 정수 최소단위와 통화를 함께 낸다. 도구 출력에 `"8,500원"` 같은 문자열을 만들지
않는다 — 서식은 화면의 일이다.

## 4. 카탈로그

### 4.1 읽기

| 도구 | 인자 | 돌려주는 것 | 상한 |
|---|---|---|---|
| `search_transactions` | 기간, 카테고리, 가맹점, 방향 | 거래 목록 | 20행(최대 50) |
| `summarize_spending` | 기간, 카테고리, 가맹점 | 지출·수입 합, 카테고리별 합 | 카테고리 30개 |
| `count_frequency` | 기간, 카테고리, 가맹점 | 건수, 날 수, 평균 간격, 회당 평균 | — |
| `compare_periods` | 기간 둘, 카테고리 | 카테고리별 합과 증감 | 카테고리 30개 |
| `detect_outliers` | 기간 | 평소 범위를 벗어난 건 | 5건 |
| `get_budget_status` | 기간 | 카테고리별 소진율·페이스 | — |
| `suggest_category` | 가맹점, 메모, 금액, 방향 | 후보 + 근거 거래 | 근거 8건 |

`suggest_category`가 근거까지 돌려주는 것이 기능 1의
핵심이다([category-suggestion-rag.md 5장](category-suggestion-rag.md#5-검색--후보와-신뢰도)).
도구 하나가 검색과 후보 산출을 함께 끝내서, `agent`는 pgvector를 모른 채로 RAG를 한다.

### 4.2 쓰기

| 도구 | 확인 | 멱등 키 |
|---|---|---|
| `create_transaction` | 임계값 이상 | `{run_id}:{seq}` |
| `update_transaction` | 임계값 이상 | `{run_id}:{seq}` |
| `delete_transaction` | **항상** | `{run_id}:{seq}` |
| `set_budget` | 필요 | `{run_id}:{seq}` |

쓰기 도구는 넷뿐이고, 늘릴 계획이 없다. 읽기 도구는 필요하면 는다.

## 5. 오류를 모델에게 보여주는 법

도구가 실패하면 예외를 위로 던지지 않는다. **실패도 관찰(observation)이다.** 모델이 읽고
다음 수를 고칠 수 있는 모양으로 내린다.

```json
{ "call_id": "call_2", "ok": false,
  "error": { "code": "validation_error", "retryable": true,
             "hint": "period는 정해진 이름 중 하나여야 한다" } }
```

| `api` 코드 | 도구가 모델에게 | 루프가 하는 일 |
|---|---|---|
| `404 not_found` | `retryable: false` | 없다고 답한다. 다시 찾지 않는다 |
| `422 validation_error` | `retryable: true` + 어느 필드가 틀렸나 | 인자를 고쳐 한 번 더 |
| `412 confirmation_required` | 실패가 아니다 — 제안으로 바꾼다 | 루프를 멈추고 사람을 기다린다(7장) |
| `409 budget_exceeded` | 금액과 초과분을 담아 내린다 | 확인 문구에 초과분을 넣어 **한 번 알린다.** 막지는 않는다 |
| `409 request_in_progress` | `retryable: false` | 기다린다. 재시도가 루프 예산만 태운다 |
| `500 internal_error` | `retryable: true` | 한 번만. 그 뒤 사람에게 넘긴다 |

- **`code`로 분기하고 `message`는 파싱하지 않는다.** 계약이 정한 규칙을 도구 계층에서도
  그대로 지킨다([../api-contract.md 5장](../api-contract.md#5-에러-응답)).
- `hint`는 우리가 쓰는 문장이다. `api`의 `message`를 그대로 넘기지 않는다 — 사용자에게
  보일 문구와 모델에게 줄 지시는 다른 글이다.
- 예산 초과를 거부로 다루지 않는 이유는 화면 규칙과
  같다([../../ui_docs/ui-design.md 4장](../../ui_docs/ui-design.md#4-에러를-화면에-옮기는-법)) —
  예산을 넘겨 쓸 자유는 사용자에게 있다.

## 6. 자리마다 도구를 좁힌다

**같은 도구 목록을 모든 자리에 주지 않는다.** 이게 이 문서에서 가장 실효가 있는 규칙이다.

| 모드 | 쓰는 곳 | 주는 도구 | 쓰기 |
|---|---|---|---|
| `classify` | 기능 1의 AI 버튼 | `suggest_category` | 없다 |
| `query` | 기능 2의 대화 조회 | 읽기 6개 | **없다** |
| `insight` | 기능 3의 리포트 | 집계 5개 | 없다 |
| `capture` | 대화로 기록할 때 | `suggest_category`, `search_transactions` + 쓰기 넷 | 확인 게이트 |
| `mcp` | 외부 AI 서비스 | 읽기 전부 | 제안까지만(`mcp.md`) |

"조회를 물었는데 거래가 지워지는 일"을 막는 방법이 둘 있다. 프롬프트에 "지우지 마"를
적는 것과, 그 자리에서 `delete_transaction`을 **목록에서 빼는** 것.
뒤쪽만 검증할 수 있다. 앞쪽은 지켜졌는지 확인할 방법이 없다.

모드는 코드가 정한다. 사용자 발화나 모델 출력이 모드를 바꿀 수 없다 — 바꿀 수 있으면
"이제 기록 모드로 전환해"라고 적힌 메모가 언젠가 들어온다.

## 7. 쓰기 도구와 확인

쓰기 도구는 호출 한 번이 두 박자로 갈린다.

```
1) 도구 호출  → 제안(proposal)을 만들고 루프를 멈춘다. api를 부르지 않는다.
2) 사용자 확인 → 같은 Idempotency-Key로 api를 부른다. X-Confirmed-By를 붙인다.
```

- 확인 전에는 `api`로 아무것도 가지 않는다. 확인 카드가 뜬 시점에 DB는 그대로다
  ([../../ui_docs/pages/chat.md 5.2](../../ui_docs/pages/chat.md#52-확인이-오가는-순서)).
- 멱등 키는 도구 계층이 `{run_id}:{seq}`로 만든다. `seq`는 그 실행에서 몇 번째 도구
  호출인지라서, 재시도해도 같은 키가
  나온다([../api-contract.md 3장](../api-contract.md#3-멱등성--같은-거래가-두-번-들어가지-않게)).
- **`dry_run` 인자를 두지 않는다.** 두면 같은 도구에 경로가 둘 생기고, 둘 중 하나만
  테스트된다. 제안은 인자가 아니라 흐름의 단계다.

## 8. 테스트

도구는 LLM 없이 전부 테스트된다([../development-rules.md 4.3](../development-rules.md#43-테스트는-llm을-호출하지-않는다)).

- **계약 테스트** — 가짜 `api` 클라이언트로 도구마다 셋을 본다: 입력 검증이 잘못된 인자를
  거부하는가, 출력이 스키마에 맞는가, `api` 오류가 5장의 표대로 번역되는가.
- **스키마 스냅샷** — 모드별 도구 목록의 JSON Schema를 파일로 고정한다. 이게 바뀌면
  **모델에게 주는 프롬프트가 바뀐 것**이다. 리뷰에서 보여야 한다.
- **상한 테스트** — 100행을 돌려주는 가짜 응답에 `truncated`가 서는지.

## 9. 도구를 바꿀 때

| 변경 | 어떻게 |
|---|---|
| 출력에 필드 추가 | 그냥 한다 |
| 입력에 선택 인자 추가 | 그냥 한다. 기본값을 준다 |
| 인자 의미 변경·필드 제거 | **새 이름으로 만든다.** 평가 세트와 대화 기록이 옛 이름을 참조한다 |
| 도구 삭제 | 평가 세트의 라벨을 같이 고친다 |

도구를 늘리거나 지우면 세 군데를 같이 고친다 — README 4장, api-contract 6장, 이 문서의
4장. 아직 반영하지 않은 줄은 [README.md 7장](README.md#7-계약에-늘어나는-것)에 모여 있고,
문서끼리 어긋나면 `python3 scripts/check_docs.py`가 잡는다.

## 10. 결정과 이유

- **왜 범용 도구를 주지 않나.** `run_sql` 하나면 도구를 늘릴 일이 없다. 대신 읽기 전용
  보장, 질의 범위 제한, 캐시, 감사 로그의 의미가 전부 사라진다. 좁은 도구는 불편한 대신
  **검증 가능한 계약**이다([chat-analytics.md 10장](chat-analytics.md#10-결정과-이유)).
- **왜 결과에 봉투를 씌우나.** `call_id`·`truncated`·`elapsed_ms`가 없으면 참조도,
  잘림 감지도, 느린 도구 찾기도 못 한다. 봉투 없이 시작하면 나중에 전부 고쳐야 한다.
- **왜 도구가 재시도하지 않나.** 도구가 안에서 세 번 시도하면 루프의 스텝 예산과 도구의
  재시도 횟수가 곱해진다. 상한이 곱셈으로 늘어나는 설계는 언젠가 터진다.
- **왜 오류를 예외로 던지지 않나.** 모델이 고칠 수 있는 실패가 대부분이다. 잘못된 인자는
  알려주면 고친다. 예외로 루프를 끊으면 사용자는 "안 돼요"만 받는다.
- **왜 모드로 좁히나.** 6장. 프롬프트는 검증할 수 없고 목록은 검증할 수 있다.

## 11. 하지 않는 것

- **`run_sql` · `http_get` · 셸 · 파일 접근.** 어떤 모드에도 없다.
- **도구 안의 LLM 호출.** 도구가 스스로 판단하면 감사 로그가 거짓이 된다.
- **복합 도구.** "조회하고 합쳐서 그려 주는" 도구는 만들지 않는다. 엮는 일은 루프가 한다.
- **도구 자동 생성.** OpenAPI에서 도구를 뽑아내면 도구 목록이 API 표면과 같아진다.
  좁게 고르는 일이 설계다.
- **모델이 도구를 정의하는 것.** 능력 범위를 모델이 늘릴 수 있으면 범위가 아니다.
