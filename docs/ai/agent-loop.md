# 에이전트 흐름 — 단발 · ReAct · plan-and-execute

## 1. 목적

"에이전트"라는 말 하나에 아주 다른 세 가지가 들어 있다. 판단 한 번으로 끝나는 것, 관찰하며
다음 수를 정하는 것, 계획을 세우고 실행하는 것. 비용도 지연도 실패하는 모양도 다르다.

기능마다 어느 흐름을 쓰는지 정해 두지 않으면 셋 중 가장 비싼 것(ReAct)이 기본값이 된다.
그게 제일 똑똑해 보이고, 튜토리얼이 대개 그걸 보여주기 때문이다. **이 문서는 흐름을
고르는 기준과 각 흐름의 정지 조건을 정한다.**

도구 쪽 규약은 [tools.md](tools.md)에 있다. 여기는 그 도구를 **몇 번, 어떤 순서로** 부를지를
정하는 층이다.

---

## 2. 흐름 셋

| | 단발 (chain) | ReAct | plan-and-execute |
|---|---|---|---|
| 모양 | 코드가 순서를 정하고 LLM은 한 자리에서 판단 1회 | 생각 → 도구 → 관찰을 반복. 매 스텝 LLM | 계획 1회 → 코드가 실행 → 조립 1회 |
| LLM 호출 | 1 | 스텝마다 1 (2~8) | 2 (계획 · 조립) |
| 예측 가능성 | 높다. 호출 수가 상수다 | 낮다. 질문마다 다르다 | 중간. 상한이 계획 크기다 |
| 병렬 | 해당 없다 | **안 된다.** 다음이 이전에 달렸다 | 된다. 단계가 서로 독립이면 동시에 |
| 맞는 때 | 판단 자리가 하나다 | 다음에 무엇을 볼지가 방금 본 것에 달렸다 | 볼 것이 미리 정해진다 |
| 전형적 실패 | 예상 밖 입력에 못 한다고 답한다 | 같은 도구를 반복하며 예산을 태운다 | 데이터를 모르고 계획해 헛호출한다 |

세 흐름은 난이도 순이 아니다. **자유도가 올라갈수록 검증할 것이 늘어난다**는 점에서
기능 셋과 같은 축 위에 있다([README.md 1장](README.md#1-네-기능)).

### 판정 한 줄

> **다음에 무엇을 부를지가 이전 결과에 달려 있나?**
> 아니오 → plan-and-execute. 예 → ReAct. 애초에 부를 것이 하나다 → 단발.

이 질문에 "잘 모르겠다"가 나오면 단발로 시작한다. 올려 붙이는 건 쉽고, 내려오는 건 어렵다.

## 3. 어느 기능에 어느 흐름인가

| 기능 | 흐름 | LLM | 왜 |
|---|---|---|---|
| 1 · 카테고리 분류 | 단발 | 0~1회 | 판단 자리가 하나다. 후보는 이미 검색이 좁혀 놓았다 |
| 2 · 대화 통계 | ReAct (짧게) | 2~4회 | "0건인데?"를 보고 다음 수를 바꾼다 |
| 3 · 상황 통계 | plan-and-execute | 2회 | 집계 여섯 개는 서로 독립이다. 동시에 부르면 된다 |
| 기록 (capture) | 단발 + 확인 게이트 | 1~2회 | 값을 뽑는 판단 하나, 가맹점을 읽었으면 이어서 기능 1의 분류. 순서는 코드가 정한다. 그 뒤는 사람이 확인한다 |

기능 1이 단발인 이유를 한 번 더 적어 둔다. 분류에 ReAct를 붙이면 모델이 "비슷한 거래를 더
찾아볼까"를 스스로 정하게 되는데, 그 판단은 이미 검색 단계가
했다([category-suggestion-rag.md](category-suggestion-rag.md)). 루프를 얹으면 지연이 배로
늘고 답은 같다.

기능 3은 plan-and-execute의 변형이다. **계획 전에 고정 호출 두 번이 먼저 간다.** 데이터를
모르는 상태의 계획은 "일단 다 불러 보자"가 되기 때문이다. 훑고 나서 계획한다.

## 4. ReAct — 기능 2의 흐름

### 4.1 상태

```python
@dataclass(frozen=True)
class Step:
    tool: ToolName
    args: Mapping[str, object]
    observation: ToolResult | None


@dataclass
class LoopState:
    run_id: RunId
    steps: list[Step]
    budget: Budget  # 스텝 · 비용 · 벽시계
```

- 관찰은 [tools.md 3.1](tools.md#31-결과-봉투)의 봉투 그대로 넣는다. 요약해서 넣지 않는다 —
  숫자를 줄이는 순간 답의 숫자가 도구 결과와 달라진다.
- 통계 대화는 짧아서 옛 스텝을 전부 들고 간다. 길어지면 오래된 관찰의 `data`부터 버린다.
  `tool`과 `args`는 남긴다. 같은 걸 또 부르지 않게 하는 데 그게 쓰인다.
- **`thought`는 저장하고 화면에는 보내지 않는다.** 사용자에게 필요한 건 "무엇을 하는 중"
  이고, 모델의 중간 생각은 검증되지 않은
  글이다([../../ui_docs/pages/chat.md 4.1](../../ui_docs/pages/chat.md#41-sse-이벤트가-화면으로)).

### 4.2 정지 조건

| 조건 | 결과 |
|---|---|
| 도구 없이 답이 왔다 | 정상 종료. 답을 검증하고 낸다 |
| 스텝 상한 (`AGENT_MAX_STEPS`) | 부분 결과 + "여기까지 해봤어요" |
| 비용·시간 상한 | 같다 |
| 같은 (도구, 인자)가 두 번 | **끊는다.** 4.3 |
| 확인 대기 | 멈춘다. LLM을 부르지 않는다(6장) |

통계 질문의 스텝 수는 보통 둘이다. 다섯을 넘으면 그건 도구로 표현되지 않는 질문이라는
뜻이고, 더 돌려도 답이 안 나온다 — 못 한다고 말하는 게
맞다([chat-analytics.md 7.3](chat-analytics.md#73-못-하는-질문)).

### 4.3 루프 감지

`(도구 이름, 인자 해시)`를 집합에 쌓는다. 같은 쌍이 두 번째로 나오면 그 자리에서 끊는다.

읽기 도구는 **다시 불러도 같은 답이 온다.** 사람은 "혹시 몰라 다시 확인"을 하지만 모델의
반복 호출에는 그런 의미가 없다. 대개 원하는 숫자가 안 나와서 같은 곳을 다시 보는 것이고,
그 다음 스텝도 같을 것이다.

끊었을 때 사용자에게 내는 건 "실패"가 아니라 그때까지 모은 숫자다. 그리고 로그에 남긴다 —
루프 감지가 자주 발동하면 도구 설명이나 도구 자체가 부족한
것이다([tools.md 2장](tools.md#2-도구-하나의-모양)).

## 5. plan-and-execute — 기능 3의 흐름

### 5.1 계획은 데이터다

계획도 자유 문장이 아니라 스키마다.

```json
{
  "steps": [
    { "tool": "compare_periods", "args": { "a": "last_month", "b": "this_month" },
      "why": "지난달과 달라진 카테고리를 보려고" },
    { "tool": "detect_outliers", "args": { "period": "this_month" },
      "why": "한 건이 합계를 먹었는지 보려고" }
  ]
}
```

| 검사 | 걸리면 |
|---|---|
| `tool`이 그 모드의 목록에 있나 | 그 단계를 버린다([tools.md 6장](tools.md#6-자리마다-도구를-좁힌다)) |
| `args`가 스키마에 맞나 | 그 단계를 버린다 |
| 같은 (도구, 인자)가 중복인가 | 하나만 남긴다 |
| 단계 수가 상한을 넘나 | 앞에서부터 상한까지만 |
| 남은 단계가 0개인가 | 고정 리포트로 간다 |

`why`는 모델이 쓰고 사람이 읽는다. 로그에 남겨 두면 "왜 이 집계를 불렀지"에 답할 수 있고,
헛계획이 늘 때 프롬프트를 어디서 고칠지 보인다. 실행에는 쓰이지 않는다.

### 5.2 실행은 코드가 한다

계획이 검증을 통과한 순간 남은 일은 기계적이다. 단계가 서로 독립이라서 동시에 부른다.

- 한 단계가 실패하면 그 단계만 비우고 나머지로 조립한다. 리포트는 덜 보여줄 수 있다.
- 실행 중에 LLM을 부르지 않는다. 계획을 고치고 싶어지는 상황이 곧 5.3이다.

### 5.3 재계획은 한 번만

실행 결과가 **전부 비었을 때만** 한 번 다시 계획한다(거래가 없는 달 등).

무제한 재계획은 ReAct인데 스텝당 계획 비용까지 더 드는 흐름이다. 한 번으로 제한하면
최악의 호출 수가 `계획 2 + 조립 1 + 집계 2N`으로 고정된다. **상한이 계산되는 흐름을
고르는 게 이 문서의 목적 중 하나다.**

## 6. 사람이 끼는 자리

쓰기가 있는 흐름에서 확인은 예외 처리가 아니라 **루프의 상태**다.

```
running → awaiting_confirmation → running → done
                    ↓ 취소
                 aborted
```

- `awaiting_confirmation`에서는 LLM을 부르지 않는다. 기다리는 동안 토큰을 태우지 않는다.
- 확인이 오면 같은 `run_id`로 이어서, 제안을 만들 때 정한 멱등 키로
  실행한다([tools.md 7장](tools.md#7-쓰기-도구와-확인)).
- 취소도 루프에 알린다. 조용히 카드만 지우면 실행은 영원히
  기다린다([../../ui_docs/pages/chat.md 5장](../../ui_docs/pages/chat.md#5-확인-카드)).
- **제안의 수명은 24시간이다.** 멱등 키 보존 기간과 같게
  맞춘다([../api-contract.md 3장](../api-contract.md#3-멱등성--같은-거래가-두-번-들어가지-않게)).
  키가 지워진 뒤에 온 확인은 재시도가 아니라 새 요청이 되므로, 만료된 제안은 다시 제안한다.

사람을 기다리는 상태를 흐름에 넣어 두면 "확인을 안 받고 질러 버리는" 경로가 생기지 않는다.
확인은 UI의 장식이 아니라 루프가 멈추는 자리다.

## 7. 실패와 재시도

| 실패 | 누가 고치나 | 몇 번 |
|---|---|---|
| LLM 출력이 스키마에 안 맞는다 | 코드가 다시 시킨다 | 1회. 그 뒤 흐름 중단 |
| 도구가 `validation_error` | **모델이** 인자를 고친다 | 같은 도구에 2회까지 |
| `api`가 `500 internal_error` | 코드가 백오프 후 재호출 | 2회. 스텝을 소모하지 않는다 |
| `409 request_in_progress` | 코드가 기다린다 | 1회. 재시도는 중복만 만든다 |
| 제공자 타임아웃·장애 | 흐름을 끊는다 | 0회. 폴백으로 간다 |
| 쓰기가 타임아웃 났다 | **같은 멱등 키로** 다시 | 1회 |

- 모델이 고칠 수 있는 실패와 코드가 고칠 수 있는 실패를 나눈다. 인자가 틀린 것은 모델의
  일이고, 네트워크는 코드의 일이다. 섞으면 재시도가 곱해진다.
- **쓰기 재시도에 새 키를 만들지 않는다.** 그게 같은 지출이 두 건 되는 유일한 경로다.
- 재시도는 흐름의 상한 안에서만 한다. 재시도 때문에 상한을 넘기는 구현은 상한이 없는 것이다.

## 8. 예산

| 상한 | 환경변수 | 기본 | 넘으면 |
|---|---|---|---|
| 스텝 | `AGENT_MAX_STEPS` | 8 | 부분 결과 |
| 비용 | `AGENT_MAX_COST_USD` | 0.50 | 부분 결과 |
| 벽시계 | 흐름마다 코드에 | 대화 20초 · 리포트 10초 | 부분 결과 |
| 집계 호출 | `INSIGHT_MAX_TOOL_CALLS` | 6 | 계획을 자른다 |

- 비용은 `litellm`이 주는 사용량으로 누적한다. 스텝마다 확인하고, 다음 스텝을 밟기 전에 끊는다.
- 세 상한 중 **무엇에 걸려 끊겼는지를 기록한다.** 벽시계에 자주 걸리면 도구가 느린 것이고,
  스텝에 자주 걸리면 흐름이 틀린 것이다. 대응이 다르다.
- 상한에 자주 걸린다고 상한을 올리지 않는다. 흐름을 고친다. 상한을 올리는 건 증상을 지우는 일이다.

끊긴 실행도 답을 낸다. "여기까지 해봤어요"와 지금까지의 숫자. 조용히 멈추지 않는다.

## 9. 상태와 재개

| 어디 | 무엇 |
|---|---|
| `agent_runs` | run 하나 — 발화, 모델, 흐름 종류, 스텝 수, 토큰, 비용, 상태, 끊긴 이유 |
| `tool_calls` | 스텝 하나 — `call_id`, 도구, 인자, 결과 요약, 확인 시각 |

- 스트림이 끊기면 브라우저가 `run_id`로 다시 붙고, 서버는 보낸 이벤트 다음부터
  이어 보낸다([../../ui_docs/pages/chat.md 4.2](../../ui_docs/pages/chat.md#42-스트림이-끊기면)).
- 서버가 재시작하면 `running`으로 남은 실행은 `aborted`로 정리한다. 되살리지 않는다 —
  중간 상태의 LLM 대화를 복원하는 값이 그 복잡도보다 작다.
- `awaiting_confirmation`은 살아남는다. 그건 LLM 상태가 아니라 제안 한 건이고,
  멱등 키와 제안 내용만 있으면 끝까지 갈 수 있다.
- 로그에 발화 원문·금액·가맹점을 넣지 않는다. 감사 테이블과 운영 로그는 다른
  것이다([../development-rules.md 6.4](../development-rules.md#64-로깅--운영-로그와-감사-로그를-나눈다)).

## 10. 평가와 관측

흐름은 "맞았나"가 아니라 **"얼마나 헤맸나"**로 본다. 정확도는 기능 문서가 본다.

| 지표 | 왜 보나 |
|---|---|
| 스텝 수 중앙값 · p95 | 중앙값이 오르면 도구가 부족한 것이다 |
| 루프 감지 발동률 | 도구 설명이 모호하다는 신호(4.3) |
| 재계획률 | 계획 프롬프트가 데이터를 덜 보고 있다는 신호(5.3) |
| 예산 중단률 | 무엇에 걸렸는지와 함께(8장) |
| 확인 대기 이탈률 | 제안이 사용자에게 납득되지 않는다는 신호 |
| 스키마 재시도율 | 출력 스키마가 복잡하다는 신호 |

회귀 테스트는 **테이프**로 한다. 고정된 LLM 응답 목록과 고정된 도구 응답을 순서대로
내놓는 가짜 둘을 끼우고, 루프가 같은 경로를 밟는지 본다. 루프 감지, 예산 중단, 재계획,
확인 대기 재개는 전부 이렇게 LLM 없이
검증된다([../development-rules.md 4.3](../development-rules.md#43-테스트는-llm을-호출하지-않는다)).

## 11. 결정과 이유

- **왜 전부 ReAct로 가지 않나.** 제일 유연하지만 호출 수가 입력마다 달라서 비용·지연·
  실패 모양이 예측되지 않는다. 가계부에서 사용자가 묻는 것은 대개 정해진 모양이다.
  유연함에 값을 치를 이유가 없다.
- **왜 단발이 기본인가.** 상한이 상수이고, 테스트가 쉽고, 실패가 한 군데서만 난다.
  기능 1이 이걸로 충분한데 루프를 얹었다면 우리는 지연만 두 배로 산 셈이다.
- **왜 계획을 검증하나.** 계획은 모델이 만든 데이터다. 검증하지 않은 데이터로 도구를
  부르면 그건 모델에게 실행 권한을 준 것이다.
- **왜 재계획을 한 번으로 묶나.** 5.3. 상한이 계산되는 흐름만 상한이 있는 흐름이다.
- **왜 중간 생각을 화면에 안 보내나.** 검증되지 않은 문장이고, 사용자는 진행 상황만
  알면 된다. 보내기 시작하면 그 문장이 제품의 일부가 되어 고칠 수 없게 된다.
- **왜 자율 루프가 없나.** 사람이 누를 때만 돈다. 스스로 도는 루프는 비용 상한이 시간에
  비례해 늘고, 아무도 안 보는 동안 틀린다([README.md 8장](README.md#8-이-폴더가-하지-않는-것)).

## 12. 하지 않는 것

- **멀티 에이전트.** 서브 에이전트를 부르는 도구를 만들지 않는다. 도구 안에 LLM을 두지
  않는다는 규칙과 같다([tools.md 11장](tools.md#11-하지-않는-것)).
- **자기 비평 루프(reflexion).** 자기 답을 다시 읽고 고치는 스텝은 호출을 배로 쓰고,
  우리가 잡아야 할 실패(숫자 지어내기)는 검증 코드가 이미 잡는다.
- **트리 탐색.** 여러 계획을 만들어 견주는 흐름. 리포트 한 장에 그럴 값이 없다.
- **백그라운드 실행.** 요청 없는 루프는 없다.
- **흐름을 모델이 고르는 것.** 흐름은 기능이 정한다(3장). 모델이 "이번엔 계획 세울게요"를
  말할 수 있으면 상한이 모델 손에 있는 것이다.
