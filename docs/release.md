# 릴리스

`develop`에 모인 것을 `main`으로 올리고 버전을 붙이는 절차.

날짜로 릴리스하지 않는다. 쓸 만한 덩어리가 됐을 때 한다.

---

## 1. 버전 규칙

[semver](https://semver.org)를 쓴다. `MAJOR.MINOR.PATCH`.

| 자리 | 올리는 때 |
|---|---|
| MAJOR | 쓰던 것이 깨진다. API 계약이 바뀌거나 데이터 이전이 필요하다 |
| MINOR | 기능이 는다. 쓰던 것은 그대로 |
| PATCH | 고친다. 동작이 바뀌지 않는다 |

`0.x`는 **언제든 깨질 수 있다는 뜻**이다. 첫 사용자가 생기기 전까지는 0으로 둔다.

- 태그에는 `v`를 붙인다 — `v0.1.0`.
- 파일 안의 버전에는 붙이지 않는다 — `0.1.0`.

태그 접두사는 저장소 설정에 들어 있다. 클론한 뒤 한 번 맞춰 준다.

```bash
git config gitflow.prefix.versiontag v
```

---

## 2. 버전이 사는 곳은 한 곳이다

저장소 루트의 **`VERSION`** 파일 한 줄. 다른 어디에도 버전을 적지 않는다.

버전이 두 군데 있으면 한쪽만 올리는 날이 반드시 온다. `CHANGELOG.md`의 맨 위 항목은
`VERSION`과 같아야 하고, 어긋나면 `scripts/check_docs.py`가 잡는다.

---

## 3. 절차

### 3.1 브랜치를 딴다

```bash
git flow release start 0.1.0
```

`release/0.1.0`이 `develop`에서 갈라진다. **여기서 하는 일은 셋뿐이다** — 버전,
변경 기록, 막판 버그. 새 기능은 넣지 않는다(5장).

### 3.2 버전을 올린다

```bash
echo 0.1.0 > VERSION
```

### 3.3 `CHANGELOG.md`를 쓴다

[Keep a Changelog](https://keepachangelog.com/ko/1.1.0/) 형식을 따른다.

- 맨 위가 최신이다.
- 항목은 **추가 / 변경 / 제거 / 수정 / 보안** 중 하나로 묶는다.
- 개발 중에는 맨 위에 `[Unreleased]`를 두고, 릴리스할 때 그 제목을 버전과 날짜로 바꾼다.

초안은 커밋 로그에서 뽑되, **그대로 옮기지 않는다.**

```bash
git log --oneline v0.0.9..HEAD     # 이전 태그가 있으면
git log --oneline main..HEAD       # 첫 릴리스면
```

커밋 메시지는 고친 사람이 읽으라고 쓴 것이고, 변경 기록은 **쓰는 사람이 읽으라고**
쓴 것이다. "refactor: tools/ → scripts/"는 쓰는 사람에게 아무 뜻이 없다.
사용자에게 달라지는 것이 없으면 아예 적지 않는다.

### 3.4 점검한다

```bash
make all                    # 검사 · 린트 · 타입 · 테스트
make review BASE=main       # main 이후 바뀐 파일
```

### 3.5 끝낸다

```bash
git flow release finish 0.1.0 -m "v0.1.0"
```

한 번에 셋을 한다 — `main`에 머지, `v0.1.0` 태그, `develop`으로 되돌려 머지.
되돌려 머지하는 걸 잊으면 릴리스 브랜치에서 고친 버그가 다음 릴리스에서 되살아난다.
`git flow`가 대신 해 주는 이유가 이것이다.

---

## 4. 배포

아직 배포 대상이 없다. 컨테이너 이미지를 어디로 올릴지 정해지면 여기에
태그 기반 빌드를 적는다. 그때까지 "릴리스"는 `main`에 태그가 붙는 것까지다.

---

## 5. 릴리스 브랜치에서 하지 않는 것

- 새 기능. 필요해지면 릴리스를 접고 `feature/*`로 돌아간다.
- 리팩터링. 버전을 올리는 김에 정리하고 싶어지는데, 그러다 릴리스가 미뤄진다.
- 문서 대청소. 변경 기록만 쓴다.

---

## 6. 체크리스트

- [ ] `VERSION`이 올랐는가?
- [ ] `CHANGELOG.md` 맨 위가 `VERSION`과 같은 버전·날짜인가?
- [ ] 변경 기록이 커밋 메시지 복사가 아니라 사용자 말로 쓰였는가?
- [ ] `make all`이 통과하는가?
- [ ] 이 브랜치에 새 기능이 섞여 들어가지 않았는가?
- [ ] `finish` 뒤에 `main`과 `develop`이 둘 다 움직였는가?

---

## 7. hotfix

운영에서 급히 고쳐야 할 때만 쓴다. `main`에서 따고 `main`으로 돌아가며,
`develop`에도 자동으로 반영된다.

```bash
git flow hotfix start 0.1.1
# 고친다. VERSION과 CHANGELOG도 같이 올린다
git flow hotfix finish 0.1.1 -m "v0.1.1"
```

절차는 릴리스와 같다. 급할수록 [점검](git-flow-guide.md)을 건너뛰지 않는다.
